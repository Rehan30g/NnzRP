# CLAUDE.md — Agent System Guide & Code Function Index

This document provides a concise architectural sitemap and function lookup table for **NnzRP**. AI agents reading this file can instantly understand the codebase structure without reading every file individually.

**Total app code is small (~5,700 lines across `js/`, excluding the vendored `marked.min.js`)** — `js/ui/views/chatView.js` is by far the largest file (~1,300+ lines) and holds most of the chat runtime logic.

---

## 🏛️ System Overview & Core Stack

- **App Name**: NnzRP (Client-Side BYOK AI Roleplay Studio)
- **Backend**: None (100% Client-Side, Browser BYOK) — all AI provider calls are direct `fetch()` from the renderer.
- **Shell**: **three parallel shells around the same `js/`/`css/`/`index.html`** — Electron desktop (`main.js` + `preload.js`, launched via `npm start` / `run.bat` → `run_electron.bat`), a PWA installable straight from Android/desktop Chrome, and a Capacitor-wrapped Android APK. There is **no Python server anymore** — `server.py` was removed; older docs (README.md, AGENTS.md) still describe it and are stale. See **Multi-platform distribution** below for how the PWA/APK/Windows builds work and how they differ from Electron.
- **Database**: Native IndexedDB (`AetheriaRoleplayDB_v2`), stores: `characters`, `chats`, `messages`, `personas`, `proxies`, `settings`.
- **Routing**: ES6 Module Router in `js/app.js`, hash-based (`#characters`, `#chat/<charId>`, `#personas`, `#settings`, `#settings/<tab>`, `#mcp`). `#proxies` is no longer a view of its own — `parseHash()` rewrites it to `#settings` with the Proxies tab preselected (see **Settings page** below).
- **UI Style**: Flat Grayish Slate, **themeable light + dark** (auto/light/dark + user-editable accent colour), No Emojis, Dedicated Fullscreen Chat Page, Storybook Per-Block Layout, Floating Input Box. See **Design system & theming** below — colours must go through CSS custom properties, not hardcoded hex. Mobile viewports additionally need `env(safe-area-inset-*)` clearance on every fixed-position edge element (status bar, gesture nav bar) — see **Multi-platform distribution**'s safe-area bullet before touching `.main-header`/`.chat-header`/`.app-sidebar`/`.chat-input-container`/`.settings-savebar`/`.toast-container`.
- **Window title**: dynamic, `NnzRP - <view>` / `NnzRP - Chat with <character>`, applied from `App.applyWindowTitle()` on every `navigate()`. `index.html`'s `<title>`, its `.titlebar-title` span, and `main.js`'s `BrowserWindow({title})` are all just the generic `NnzRP` fallback for the instant before the first route renders.
- **Packaging**: `electron-builder` (see `package.json` `build` block) → `dist/` (win-unpacked, nsis/zip/portable) locally via `npm run build:exe`, or in CI via `.github/workflows/build-windows.yml`. `dist/` and `venv/` are build/py-tooling artifacts, not app source — ignore when searching code.

## 📱 Multi-platform distribution (PWA / Android APK / Windows installer)

The same `js`/`css`/`index.html` now ships three ways beyond the original Electron build. The load-bearing design choice: **the Android APK is a thin shell that loads the app LIVE from GitHub Pages** (`capacitor.config.json`'s `server.url`) instead of bundling a snapshot — pushing a frontend change to `master` reaches the installed APK on its very next launch with **no rebuild, no reinstall**. Electron and the Windows installer are the opposite: fully bundled local builds (`main.js` `loadFile()`s `index.html` directly), so they genuinely need a fresh build/install whenever the app changes.

- **`browser-mode`**: `index.html`'s pre-paint script stamps `document.documentElement.classList.add('browser-mode')` whenever `window.electronAPI` is absent (PWA, plain browser tab, and the Android APK all hit this — Capacitor's WebView doesn't inject `electronAPI`). `.browser-mode .custom-titlebar { display:none }` / `.browser-mode #app { height:100dvh }` (`css/layout.css`) hide the Windows-style frameless titlebar and reclaim its 36px on every non-Electron target.
- **PWA layer**: `manifest.json` + `sw.js`, registered from `index.html` only `if (!window.electronAPI && 'serviceWorker' in navigator)`. `sw.js` deliberately does **not** hardcode a precache file list (the codebase has 40+ plain-relative-import JS modules with no `?v=` busting, unlike the top-level `<script>`/`<link>` tags — a hardcoded list would be a second place to keep in sync and WILL drift). Instead it's stale-while-revalidate on every same-origin `GET`: serves cached instantly, updates the cache from the network in the background, and never touches cross-origin requests (BYOK provider calls, HTTP MCP servers) or non-GET requests. Bumping a CSS/JS file's `?v=` query in `index.html` is still required for that file's *own* cache entry to bust immediately rather than on the load-after-next.
- **Serving**: `serve.js` (zero-dependency Node static server, `npm run serve`) for local testing only. The real deployed site is **GitHub Pages**, auto-published by `.github/workflows/deploy-pages.yml` on every push to `master` that touches `index.html`/`css/**`/`js/**`/`src/**`/`manifest.json`/`sw.js` — deliberately excludes `android/**` and the workflows themselves, so routine content pushes never trigger (or need) a native rebuild.
- **Android APK (Capacitor)**: `capacitor.config.json` (`appId: com.nnzrp.app`, matching Electron's `electron-builder` appId), native project at `android/` (`npx cap add android` — re-sync after adding any Capacitor plugin or changing `capacitor.config.json` via `npx cap sync android`). `.github/workflows/build-apk.yml` is **manual-only** (`workflow_dispatch`), never on push — it's only needed for native-shell changes (icon, permissions, `appId`, Capacitor/Android SDK version, or a new native plugin like `@capacitor/app`, see the back-button bullet below). Release signing: `android/app/build.gradle`'s `signingConfigs.release` reads `ANDROID_KEYSTORE_PATH`/`ANDROID_KEYSTORE_PASSWORD`/`ANDROID_KEY_ALIAS`/`ANDROID_KEY_PASSWORD` from env vars (each `?.trim()`'d — a stray trailing newline picked up when a secret's value was pasted into GitHub's UI produces the exact same "Given final block not properly padded" JCE error as an actually-wrong password), all sourced from GitHub repo secrets and **never hardcoded**; absent env vars just skip signing (local `gradlew assembleRelease` still works, unsigned) rather than failing the build. **The keystore itself must be a single-password PKCS12** (modern `keytool`'s default type) — giving `-storepass`/`-keypass` two *different* values silently "succeeds" at `keygen` but then fails to decrypt for every consumer, since PKCS12 doesn't really support a separate per-key password the way legacy JKS did; always generate with `-storepass X -keypass X` (same value).
- **Windows installer**: `.github/workflows/build-windows.yml`, also manual-only, runs the exact same `npm run build:exe` (`electron-builder --win nsis zip portable --publish=never`) a local build would. The `--publish=never` is required in CI specifically — `electron-builder` auto-detects `GITHUB_ACTIONS` and tries to check for a `GH_TOKEN` to decide whether to self-publish even without `--publish` requested, failing the whole build if absent; releases are published separately by this workflow's own `softprops/action-gh-release` step instead.
- **One shared release**: both `build-apk.yml` and `build-windows.yml` publish to the same fixed `latest` GitHub Release tag (via `softprops/action-gh-release`, which adds/updates assets rather than clearing them), so there's always one bookmarkable page with a current download for each platform regardless of which workflow last ran.
- **Safe-area insets (`env(safe-area-inset-*)`)**: the installed Android APK draws edge-to-edge behind the OS status bar and gesture-navigation bar, unlike a normal browser tab. Every fixed-position element that touches a screen edge on mobile needs the corresponding inset added, always with a `, 0px` fallback so desktop/browser rendering is byte-identical: `.main-header`/`.chat-header` (`padding-top`/height), `.app-sidebar`'s mobile bottom-nav (`padding-bottom`/height), `.chat-input-container` (`bottom`), `.toast-container` (`top`), `.settings-savebar` (`bottom` — must track `.app-sidebar`'s actual height, not a bare `60px`). Anything that computes a height/padding *relative to* one of these (`.messages-container`, `.view-container`) must grow by the same inset too, or content ends up hidden behind the now-taller edge element — this exact chain of missed downstream spots is why the fix landed in several passes; when adding a new mobile fixed-position element, grep for the existing `env(safe-area-inset-` call sites first rather than re-deriving it.
- **Android back button**: `@capacitor/app`'s `backButton` listener, wired in `js/app.js`'s `init()` behind `window.Capacitor?.Plugins?.App` (a no-op everywhere except the installed APK — Electron/browser/PWA never see this global). Fully overrides Capacitor's un-customized default (single-press `goBack()`-then-exit): from any view other than `characters`, back navigates to `characters` instead of exiting; from `characters` itself, exiting needs two presses within 2s (`Toast.info` hint on the first), the standard Android "press back again to exit" pattern. Adding this plugin required a native re-sync (`npx cap sync android`) and counts as a native-shell change (needs `build-apk.yml` re-run), unlike pure `js/`/`css/` edits.
- **`.gitignore`**: `android/app/build/`, `android/build/`, `android/.gradle/`, `android/local.properties`, `*.keystore`, `*.jks` — the release keystore must never be committed; it only ever exists as the 4 GitHub secrets above (generated once locally with a throwaway portable JDK, never through CI on this **public** repo, where Actions artifacts are publicly downloadable by anyone).

## 🎨 Design system & theming

The app ships a full light **and** dark palette plus a user-editable accent colour. Three moving parts:

- **Tokens (`css/variables.css`)** are the only place a raw colour may be written. Light values sit on `:root`; the dark palette appears twice — `:root[data-theme="dark"]` and, inside `@media (prefers-color-scheme: dark)`, `:root:not([data-theme="light"])`. That `:not()` is what lets an explicit **Light** choice beat a dark OS. **The two dark blocks must be kept in sync** (CSS has no way to share one block across a media-query boundary).
- **Mode resolution**: `'auto'` deliberately **removes** `data-theme` entirely rather than resolving the OS preference in JS — the media query then decides, so the app follows a live OS theme switch with zero listeners. `'light'`/`'dark'` stamp the attribute. `data-theme-mode` always carries the raw preference so the Appearance segmented control can show which of the three was actually picked.
- **Persistence** is IndexedDB (`ThemeStore`), mirrored to localStorage **only** so `index.html`'s synchronous head script can apply the theme before first paint. Without that mirror a dark-theme user gets a white flash on every launch. `initTheme()` re-reads IndexedDB on boot and refreshes the mirror if they diverged (e.g. after a backup restore).
- **Accent customisation** writes `--accent-primary`/`--accent-secondary` as **inline styles on `<html>`**, which outrank both palettes. Everything else is derived at runtime with `color-mix()` rather than stored: the soft washes mix into `var(--bg-surface)` and the hover/text shades mix toward `var(--text-main)` — so one picked colour stays correct when the theme flips (darkens in light mode, lightens in dark mode). Picking the default indigo pair **removes** the overrides so each theme's own tuned accent applies. `--text-accent` is specifically NOT the raw hex: a mid-tone accent like emerald `#059669` is unreadable as label text on the dark `--accent-primary-soft` tint.
- **Hardcoded hex is a bug.** Before this work, colours were scattered as inline `style="background:#f8fafc"` strings across the view files, which is exactly what made dark mode hard. The CSS tree is now token-only (the single exception is the always-white icon on the red titlebar close button). In JS the only surviving literals are the `ACCENT_PRESETS` swatch definitions, `ThemeStore`'s defaults, an HTML entity, and `app.js`'s catastrophic-boot-failure screen (which keeps hex fallbacks on purpose — it must render even if theming never initialised).

### Toggle switches

Every boolean setting renders through `toggleSwitchHTML()`/`toggleRowHTML()` (`js/ui/components/toggle.js`); there are **no bare checkboxes left in `js/ui/`**. It is a visual wrapper only — the real `<input type="checkbox">` survives with its id, classes, `data-*`, `.checked` and `.disabled`, so existing logic like `mcpImmersiveToggle.disabled = !enabled` or `container.querySelector('#setting-streaming-enabled').checked` keeps working verbatim. Use `small: true` for dense list rows (per-server MCP toggles, the OpenRouter provider picker).

### Custom dropdown

`js/ui/components/dropdown.js` replaces every native `<select>`. Two decisions are load-bearing:

1. **A hidden `<input type="hidden" id="{id}">` carries the value.** That is why every pre-existing read path (`container.querySelector('#setting-active-proxy').value`, `document.getElementById('proxy-provider').value`, …) still works untouched after the swap. Selecting also dispatches a native `change` event on it, so legacy `el.onchange = fn` wiring fires too — `wireDropdown`'s `onChange` callback is just the nicer path. The `.dropdown` root element gets id `{id}-dropdown` and `data-dropdown-for="{id}"`.
2. **The option list is portalled to `<body>` and positioned `fixed`,** never nested under the trigger. Two call sites make this mandatory: modal forms (`.modal-body` is `overflow-y:auto` and would clip it) and the chat composer model picker (`.chat-input-container` has `transform: translateX(-50%)`, which makes it a containing block for `position:fixed` descendants and would trap the menu). Only one menu is open app-wide (`openState`).

Options are `{value, label, hint?, disabled?}`; the optional `hint` renders as a dimmed second line — the actual reason this isn't a restyled `<select>` (native options can only hold flat text). The menu is built with `createElement` + `textContent`, never `innerHTML`, so option labels (proxy names, model ids, persona names) need no escaping by callers.

**Keyboard handling has one trap**: the open menu's `keydown` listener is registered on `document` in the **capture** phase, and must call BOTH `preventDefault()` and `stopPropagation()`. Without `stopPropagation`, Enter closes the menu in the capture handler and the same event then reaches `triggerEl.onkeydown`, which sees `openState === null` and immediately re-opens it — the menu appeared never to close on selection. (Caught only by live testing, not code review.) Stopping it there also means Escape closes just the dropdown, not the chat drawer's window-level Escape handler underneath it.

## 🧠 chatView.js internals (worth knowing before touching it)

- **Module-level singleton generation state**: `activeAbortController`, `isGenerating`, and now `queuedMessage`/`queuedMessageHandlers` are module-scope variables, not instance state — deliberate, since only one `ChatView` is ever mounted at a time in this SPA (see comment at top of the file). Don't refactor this into per-instance state without re-checking that assumption still holds.
- **Streaming vs non-streaming** both funnel through `AgentRunner.run()` (which internally calls `ProviderManager.sendChatCompletion`/`streamChatCompletion` in a loop for MCP tool-calling — see **MCP tool-calling** below), then `mergePrefillResult()` re-splits `<think>` tags after gluing the prefill text back onto the model's first-round continuation only (passed to `AgentRunner` as `transformFirstResult`, not applied to later tool-result-driven rounds).
- **The composer is never disabled**, including mid-generation — `setGeneratingState()` only re-skins the send button into a stop button; it does not touch `#chat-input`. Submitting while `isGenerating` queues the text (`queuedMessage`) instead of sending, shown via `#queued-message-indicator`, and auto-flushes through `flushQueuedMessageIfAny()` in the `finally` block of both `triggerAIGeneration` and `handleSwipeNext` once the in-flight generation ends (success or abort). `queuedMessage` is deliberately cleared on every session switch/new-session/delete (search `clearQueuedMessage()`) so a draft typed in one chat can never fire into another.
- **Swipes**: `handleSwipeNext` only allows generating a *new* variation on the last assistant message; older messages must be forked first (`ChatStore.forkChat`) before they can be regenerated. One swipe variation = one whole generation turn including all of its MCP tool rounds (see "ONE assistant message per user turn" below) — a variation is never split across messages.
- **Deleting a user message cascades to its reply** (`ChatStore.deleteMessage`). The delete button's `confirm()` text and toast adapt to whether a cascade will happen, so the user is told before more than the clicked message goes away.
- **The MCP permission prompt is a card inside `.chat-input-container`, deliberately NOT a `Modal`.** `requestToolPermission(call, signal)` (module-level, shared by both generation call sites and wired into `AgentRunner` as `onPermissionRequest`) reads the stored permission first and only surfaces UI for `'ask'`; `showToolPermissionPrompt()` then inserts `.tool-permission-prompt` as the **first child** of `.chat-input-container`. That container is bottom-anchored (`bottom: 24px`) with auto height, so an added first child grows the box *upward* and lands the prompt exactly on top of the input — which is what "dialog di atas input pesan" asked for, and what a full-screen blocking `Modal` would not have given. Because the container is `pointer-events: none` (clicks fall through to the message stream), the card must opt its own clicks back in with `pointer-events: auto`, same as `.chat-input-wrapper`. The card shows the qualified tool name **and** the pretty-printed arguments (both `escapeHtml()`'d — they're model-generated untrusted text) so the choice is informed, with No / Always Allow / Yes. "Yes" is a **one-time** allow (nothing persisted, the same tool asks again next call); only "Always Allow" writes `'allow'` via `MCPToolRegistry.setToolPermission()`. Only one prompt can be open at a time (`activePermissionCleanup`, module-level like the other generation state); `removeToolPermissionPrompt()` force-closes it **as a refusal** and is called from both `finally` blocks. A refused call also renders in the live `.tool-live-block` as a third state (`.tool-live-item-declined`, rose cross — not a spinner, not a check) via the new `onToolDeclined` callback. See **MCP tool permissions** below for the storage/default-safety side.
- **`formatRoleplayMarkdown()`** always `escapeHtml()`s raw text *before* running it through `marked.parse()` — this is the load-bearing XSS guard for chat content (AI output and user input both flow through here). Don't bypass it.

## 🔌 MCP (Model Context Protocol) tool-calling

A first attempt at this (commit `138bf8e`) was fully reverted (`693754f`) because it only ever **injected a text description of tools into the system prompt** with no actual function-calling wire-up — the model had no structured way to call anything, so it either narrated pretending to or ignored the instruction. The current implementation (rebuilt from scratch, same file names, different contents) does real provider-native function-calling instead:

- **Trust boundary**: the LLM can only ever choose *which already-user-configured tool to call* and *what JSON arguments to pass*. It never configures, launches, or points at a new MCP server itself — `command`/`args`/`env`/`endpointUrl` are only ever written by the user through `mcpView.js`.
- **Transports**: `http` (direct `fetch()` JSON-RPC from the renderer, `mcpClient.js`) and `command`/stdio (spawned as a child process from `main.js`, talked to via the `window.electronAPI.mcp` bridge from `preload.js` — newline-delimited JSON-RPC over stdin/stdout, request/response correlated by `id` in `main.js`'s `mcpProcesses` map).
- **Flow per chat generation** (`chatView.js` → `triggerAIGeneration`/`handleSwipeNext`): `MCPToolRegistry.getActiveTools()` → `PromptBuilder.buildPromptPayload({..., tools})` → `AgentRunner.run({proxy, initialPayload, tools, streaming, ...})`. `AgentRunner` calls `ProviderManager`, and whenever the response includes `toolCalls`, runs each one past the user's permission gate (`callbacks.onPermissionRequest` — see **MCP tool permissions** below; by default this prompts above the composer), executes the allowed ones via `MCPToolRegistry.executeTool()` and loops (bounded by `settings.mcpMaxToolIterations`, default 6) — this is what lets a character call tools more than once per user turn.
- **Per-provider wire format** lives entirely in `providerManager.js` (`toOpenAIMessages`/`toAnthropicMessages`/`toGeminiContents` + matching `build*ToolsParam` builders) — `AgentRunner`/`chatView.js` stay provider-agnostic and only ever see the normalized `{role, content, toolCalls?}` / `{role:'tool', toolCallId, toolName, content}` shape. Streaming tool-call deltas (fragmented JSON args for OpenAI/Anthropic, whole objects for Gemini) are assembled by `js/utils/toolCallAccumulator.js`.
- **Regression invariant**: when `tools` is empty (no MCP servers enabled), every one of these code paths is a no-op passthrough — `buildXToolsParam` returns `undefined`, the message translators return the exact same shape as before, and `AgentRunner`'s loop exits after one iteration. A tool-less character/session should behave byte-for-byte like it did before this feature existed; if you're debugging a regression in plain (non-MCP) chat, suspect a bug in one of these translators before suspecting unrelated code.
- **UI**: `mcpView.js` (`#mcp` route) for full CRUD + a live "Discover Tools" test button; the chat right-drawer's 3rd tab ("MCP (Exp)") for a lighter per-session enable/disable + status check. Both auto-run a status check for every listed server as soon as they render (`silent: true`, no toast spam) instead of requiring a manual "Check Status" click first. A message's `toolTrace` (if any) renders as a collapsible "Tools Used" chip next to the thinking block, marked with a wrench icon (`WRENCH_ICON_SVG`) so it's visually distinguishable from a plain thinking block — `.tool-trace-block` is deliberately a *different* CSS class from `.thinking-block` so the live-streaming `syncThinkingBlock()` DOM lookup can never accidentally grab it.
- **Startup warm-up**: `js/app.js`'s `init()` fire-and-forgets `MCPToolRegistry.getActiveTools()` right after `initDatabase()` (never awaited — must not block app boot on a slow/unreachable server) so enabled servers' tool lists are cached and stdio child processes are already spawned by the time the user opens a chat.
- **Live tool-execution box during generation**: `onToolExecuting` must never overwrite the streamed reply text in the typing indicator (`typingContentEl`)/swipe content (`contentEl`) — it did originally, which made the in-progress reply visibly vanish and reappear once the round committed. It also must not be merged into the live thinking block (tried that too — read as buried/easy to miss). The fix is `syncLiveToolBox(containerEl, calls)`: its own violet-accented `.tool-live-block` element (own CSS class, not `.thinking-block`/`.tool-trace-block`) inserted before `.message-content`, with a wrench icon and a spinner per in-flight call (`{id,name,done}`), updated live via `onToolExecuting`/`onToolResult`. It's purely transient — torn down (`syncLiveToolBox(el, [])`) once the round commits or generation ends, at which point the persisted `.tool-trace-block` (via `syncToolTraceBlock`) is the permanent record. Both `triggerAIGeneration` and `handleSwipeNext` have their own copy of this wiring; `refreshMessageBlock` (swipe success path) and `restoreOriginal` (abort/error paths) both explicitly clear it too, since it's easy to leave stray if you add a new exit path.
- **Streaming render is time-throttled, deliberately NOT via `requestAnimationFrame`**: `onContentChunk`/`onThinkingChunk` used to re-run `formatRoleplayMarkdown()` (a full markdown re-parse of the *entire* accumulated reply so far, not incremental) and write straight to the DOM on every single raw SSE chunk — expensive for a long reply, and bursty chunk delivery (a client recovering from a network stall) could fire dozens of these back to back. A first fix used `requestAnimationFrame` to coalesce updates, which made things *worse and inconsistent* in practice: Chromium heavily throttles rAF (and timers) once the window loses focus/visibility, so text would stall for seconds while the window was unfocused then dump in a burst on refocus - a bigger regression than the original bursty-chunks problem. The actual fix is `createThrottledRenderer(renderFn, minIntervalMs=50)` in `chatView.js`: a plain `Date.now()` wall-clock gate checked synchronously inside the normal chunk-arrival flow, with no dependency on the renderer being foregrounded. `main.js`'s `BrowserWindow` also now sets `backgroundThrottling: false` as a second, independent layer of defense against focus-dependent slowdowns for this and any other timer-driven UI. **Do not reintroduce `requestAnimationFrame` for this path** — it's the specific thing that made the reported bug worse.
- **ONE assistant message per user turn, however many tool rounds it took** (this replaced an earlier "Claude-Code-style interleaved tool turns" design that committed a separate chat message per tool round — that design was reverted because it read as broken in practice: the pre-tool narration looked like it *disappeared*/got replaced by the post-tool text, and on swipe it produced visibly duplicated text). `AgentRunner.run()` now accumulates every round's `content`/`thinking` in `contentParts`/`thinkingParts` and returns them joined with a blank line, alongside the aggregate `toolTrace` — so the narration a model writes *before* calling a tool ("let me look that up") and the answer it writes *after* are one message, exactly what a user expects when they later swipe it as one unit. `joinParts()` deliberately returns a single-element array's part **verbatim** (no filtering/trimming) so the tool-less path stays byte-for-byte identical — see the regression invariant above.
- **`callbacks.onRoundComplete({content, thinking, toolTrace})`** (renamed from `onIntermediateMessage`, and now wired by *both* `triggerAIGeneration` and `handleSwipeNext`) fires at each tool-round boundary with everything accumulated **so far**, and is a *live-display re-sync* signal, **not** a "commit a message" signal. Both callers do the same thing with it: `liveContent = content ? content + '\n\n' : ''` (likewise `liveThinking`), then force a render. This is load-bearing in two directions — set it to `''` instead and the pre-tool narration visibly vanishes for the rest of the generation; omit the callback entirely (which is what `handleSwipeNext` used to do) and the next round's chunks get concatenated onto the previous round's text with **no separator**, which is exactly the "double chat"/garbled-duplicate rendering that was reported. The `'\n\n'` suffix matches the separator `joinParts()` will use, so the live view stays byte-identical to what finally gets persisted.
- **Empty-narration rounds need no special handling anymore**: tool-calling models very often call a tool with *no* lead-in text (confirmed with gpt-4o-mini). Under the old per-round-message design that produced a near-blank message right before the real reply, which needed a `pendingToolTrace` accumulator to fold forward; now that every round folds into one message by construction, that whole mechanism is gone. An empty round just contributes an empty part that `joinParts()` drops. `scheduleContentRender` falls back to the "…sedang mengetik…" placeholder whenever `liveContent` is still blank, so a turn that opens with a tool call doesn't flash an empty bubble.
- **`createThrottledRenderer(...).flush()` must be called wherever streaming pauses** — this fixed a reported "the reply is cut by exactly one character" bug (`"fine ill search that"` displaying as `"fine ill search tha"`). The throttle gate silently drops whatever arrived in the last `minIntervalMs` window; normally the authoritative commit repaints right after, but when the model stops mid-reply to call an MCP tool, that dropped tail sat on screen for the *entire* runtime of the tool. Both callers now `flush()` in `onToolExecuting` (streaming just paused) and in `onRoundComplete` (buffers just re-seeded). Note the streaming/SSE stack itself was verified NOT to truncate: `ThinkingStreamParser` only ever holds back a trailing partial `<`-prefixed tag, and `ProviderManager._consumeSSE` was tested byte-by-byte against a fake OpenAI SSE stream — don't go looking for the off-by-one there again.
- **The small always-visible tool marker (`.tool-inline-note`) is placed AT the tool-call boundary inside the message, not glued below the whole thing.** A single assistant message can contain narration written before a tool call AND narration written after (`AgentRunner.run()`'s `joinParts()` glues per-round parts with a blank line — see the "ONE assistant message per user turn" bullet above), e.g. `"fine ill search that\n\nhere's what i found..."`. The confirmed UX places the marker exactly between those two: `"fine ill search that" / [🔧 websearch_search] / "here's what i found..."`. This needed a data-model change, not just a DOM move, because the persisted flat `content` string alone doesn't record WHICH tool calls belong at WHICH point (splitting on `\n\n` at render time is fragile — a model's own reply can legitimately contain blank lines). `AgentRunner.run()` now also returns `segments: [{text, tools}, ...]`, one entry per round (`text` = that round's own lead-in, `tools` = that round's own slice of `toolTrace`; the final segment has no `tools`), and includes the same breakdown in the `onRoundComplete` callback payload. `ChatStore.addMessage()`/`updateMessageSwipes()` persist this as an optional `toolSegments` field alongside the existing `content`/`toolTrace` (which keep their exact old shape/meaning — other code depends on them); like `thoughts`/`toolTrace`/`images`/`embeds`, each swipe variation's own `toolSegments` is retained in `message.swipeMeta` (see the `chatStore.js` row above), not just the active one. In `chatView.js`, `renderMessageBodyHTML(msg, formatFn, userName, charName)` (module-level, near `toolTraceNames()`) is the single source of truth for a message's content area: when `msg.toolSegments` has at least one round with `tools.length > 0` (`hasToolSegments()`), it groups the segments via `groupToolSegments()` (see next bullet) and renders one `.message-content` block per text group interleaved with a `.tool-inline-note` marker (`toolInlineNoteHTML()`) at each boundary; every segment's text still goes through `formatFn` (`ChatView.formatRoleplayMarkdown`), so macros/escaping/markdown aren't skipped. **Backward compat**: messages persisted before `toolSegments` existed (or with none at all) have no segment with `tools.length`, so `hasToolSegments()` is false and it falls back to the exact old single-blob-+-trailing-note rendering driven by the flat `toolTrace` — old data never crashes or renders blank. `renderMessages()` uses `renderMessageBodyHTML()` directly to build the HTML string; the swipe paths (`refreshMessageBlock`, and `restoreOriginal` in `handleSwipeNext`) use its DOM-surgery counterpart `syncMessageBody(containerEl, msg, formatFn, userName, charName)`, which removes whatever `.message-content`/`.tool-inline-note` elements are currently in a mounted block (a stale variation may have had a different number of segments than the fresh one) and re-inserts fresh ones anchored right before `.message-footer`. `syncToolInlineNote()` no longer exists — it's fully replaced by this segment-aware pair. Partial saves on abort (`liveContent` may include a round's text beyond what the last `onRoundComplete` saw) deliberately pass no `toolSegments`, falling back to the old rendering for that message rather than risking a mismatched segment breakdown. The collapsible `.tool-trace-block` above the text (full args/results behind a click) is unrelated and unchanged by any of this — it still renders once per message from the flat `toolTrace`, same as before. **Editing invalidates segments**: `ChatStore.updateMessageContent()` clears `toolSegments` to `[]` whenever a message's text is manually edited, since the old per-round text boundaries no longer match the new text — rendering falls back to the flat `content`/`toolTrace` note instead of showing stale segment text. `chatView.js`'s edit-message handler (`.btn-edit-message`) accordingly removes ALL `.message-content`/`.tool-inline-note` elements for that message (not just the first one it finds) before showing the textarea, and restores via `syncMessageBody()` on cancel rather than stashed `innerHTML`.
- **Consecutive tool-call rounds with no narration between them get merged into ONE marker with a "(Nx)" count**, instead of rendering as several stacked `.tool-inline-note` lines sandwiching invisible empty `.message-content` divs (a model very often calls a tool with zero lead-in text, and can do that across several rounds in a row). `groupToolSegments(segments)` (module-level, shared by `renderMessageBodyHTML` and `renderLiveBodyHTML`) flattens a `toolSegments` array into a text/tools event stream and merges adjacent `tools` groups that have no non-empty `text` group between them, concatenating their tool-call arrays. `toolInlineNoteHTML(toolTrace)` appends a `(Nx)` suffix whenever the group it's given represents more than one individual call — `toolTrace.length`, not the de-duplicated name count — so calling the *same* tool 3 times still reads as "3x" instead of silently looking like one call, and this applies identically whether the merged calls are the same tool repeated or different tools called back-to-back (both confirmed as the wanted behavior, not just the same-tool case).
- **The live in-progress typing indicator/swipe streaming preview shows the same inline tool markers as the persisted message, live, as each round resolves** — this was originally scoped as a "nice to have, skip if not cheap" and initially skipped; a later report ("the note doesn't show up until streaming finishes") turned it into a requirement. `renderLiveBodyHTML(committedSegments, currentText, placeholderHTML, formatFn)` is the live counterpart to `renderMessageBodyHTML`: `committedSegments` is exactly the `segments` array `AgentRunner`'s `onRoundComplete` callback hands back each round boundary (every round that's fully finished, its own tool call(s) already attached), `currentText` is the round currently streaming in (no `tools` yet), which always gets its own trailing block and falls back to `placeholderHTML` ("…sedang mengetik…" / "Menggenerasi variasi baru…") while still empty. Both `triggerAIGeneration` and `handleSwipeNext` track `liveSegments`/`currentRoundText` alongside the pre-existing `liveContent` (`liveContent` is untouched and still the source of truth for the abort-partial-save path — `currentRoundText` is purely a rendering concern, reset to `''` at each `onRoundComplete` while `liveSegments` is reassigned wholesale to whatever `segments` that round handed back). Because a round's marker only shows once `onRoundComplete` fires (i.e. after the tool has actually finished, not while it's still executing), the violet `.tool-live-block` spinner box and this small dim marker are complementary, not redundant: the violet box is "this tool is running right now / here's the running tally for this turn", the dim marker is "this is exactly where that finished tool sits in the text once it's done" — don't try to merge them. Since the typing indicator / swipe streaming host can now contain SEVERAL `.message-content` blocks instead of one, `#typing-indicator-content` (triggerAIGeneration) and the swipe path's content host are now plain unstyled wrapper divs, not `.message-content` themselves — `renderLiveBodyHTML`'s output supplies the real `.message-content` div(s) inside them.
- **`findContentAnchor(containerEl)` exists because `insertBefore` requires a DIRECT child** — `syncThinkingBlock`/`syncToolTraceBlock`/`syncLiveToolBox` all position their block by doing `containerEl.insertBefore(block, <the .message-content element>)`. That's fine for a persisted message, where `.message-content` is always a direct child of `.message-block-inner`, but broke (`NotFoundError` at runtime) once the live-generation content host started wrapping its `.message-content` block(s) in an intermediate div (previous bullet) — `.message-content` was then a grandchild, not a child, of the container being passed in. `findContentAnchor` walks `containerEl`'s direct children and returns whichever one either *is* `.message-content` or *contains* it, so both the flat (persisted) and wrapped (live) shapes resolve to a valid `insertBefore` target. If you add a fourth `sync*ThatInsertsBeforeContent` helper, use this instead of a raw `querySelector('.message-content')`.
- **`.tool-inline-note`'s visible gap from the text above/below it is controlled entirely by its own margin, not by `marked.parse()`'s paragraph margins** — `.message-content` has no padding/border, so a wrapped `<p>`'s browser-default ~1em margin escapes it and collapses with `.tool-inline-note`'s own (much smaller) margin; the larger one silently wins, which made the note sit noticeably farther from the text than its `margin: 0.3rem` suggested. Fixed in `css/chat.css` with `.message-content:has(+ .tool-inline-note) > :last-child { margin-bottom: 0; }` and `.tool-inline-note + .message-content > :first-child { margin-top: 0; }` (Chromium in Electron 31 fully supports `:has()`) — don't try to fix this by just increasing/decreasing `.tool-inline-note`'s own margin, the collapsing paragraph margin will keep dominating until these are in place.
- **`.tool-trace-block` (persisted) vs `.tool-live-block` (in-progress) are deliberately styled differently**: the live one is prominent (violet border/text, spinner) since it needs to grab attention while something is actively happening; the persisted one is small and neutral gray (`#f8fafc`, dim text) since it's just a quiet historical record once a message is committed — don't make these look the same, that was tried and read as visual noise.
- **OpenRouter provider routing**: a proxy with `provider === 'openrouter'` can carry `openrouterProviders: string[]` (preferred underlying-provider names, e.g. `['Together', 'Fireworks']`) and `openrouterAllowFallbacks` (bool, default true), set via `proxiesView.js`'s "Browse Providers" button — a live, unauthenticated `GET https://openrouter.ai/api/v1/models/{author}/{slug}/endpoints` fetch showing each provider's context length, pricing, uptime, and throughput. `providerManager.js` applies these as OpenRouter's native `provider: {order, allow_fallbacks}` routing field on the request body (both `sendChatCompletion` and `streamChatCompletion`), gated strictly on `provider === 'openrouter'` so `openai`/`custom` proxies sharing that same code branch are unaffected.
- **Multi-model proxies + chat-side model switcher**: for `provider === 'custom'`/`'openrouter'` proxies, `proxiesView.js` has an "Additional Model IDs (comma separated)" field (same parsing convention as `charactersView.js`'s tag input) stored as `proxy.models: string[]`, independent of `proxy.selectedModel` (the one currently in use — no relationship is enforced between the two fields). `chatView.js` reads this in `populateModelSelect()` to render a compact `<select id="chat-model-select">` in the composer toolbar next to the send button (Claude-style) — picking a model there just updates `proxy.selectedModel` via `ProxyStore.save()` and calls `onProxyChanged`. Falls back to a single disabled option showing just `selectedModel` when `models` is empty/absent. Re-populated after switching the active proxy and after closing the "Multi-Proxy Config" modal from the drawer, not just once at chat-open time.
- **Global MCP master switch + Immersive Roleplay mode**: `MCPStore.getGlobalEnabled()/setGlobalEnabled()` (`settings` key `mcpGlobalEnabled`, default `true`) is a kill switch that sits above every individual server's `enabled` flag — `MCPToolRegistry.getActiveTools()` checks it first and short-circuits to `[]` (skipping all network/discovery work) when off, so it composes for free with the "empty `tools` = byte-for-byte passthrough" regression invariant above. `MCPStore.getImmersiveRoleplay()/setImmersiveRoleplay()` (key `mcpImmersiveRoleplay`, default `false`) is a separate opt-in flag read into `PromptBuilder.buildPromptPayload({..., immersiveRoleplay})` — when true *and* `tools.length > 0`, it appends a `[Immersive Tool Use]` block telling the model to reach for tools proactively as part of staying in character (e.g. a websearch tool while a character "browses", pulling current info mid-scene) instead of only on explicit request. Both toggles are plain checkboxes duplicated in two places that must be kept in sync if UI changes: the home `#mcp` route (`mcpView.js`, `#mcp-global-toggle`/`#mcp-immersive-toggle`) and the chat right-drawer's MCP tab (`chatView.js`, `#drawer-mcp-global-toggle`/`#drawer-mcp-immersive-toggle`) — each copy re-reads from `MCPStore` on render, so no cross-instance event wiring is needed. The Immersive checkbox is disabled (and the server-list section dimmed) whenever the master switch is off, purely as a UI affordance — the actual gating happens in `MCPToolRegistry`/`PromptBuilder`, not in the disabled attribute.

## 🛡️ MCP tool permissions (Ask / Allow / Decline)

Before this existed, an enabled+connected MCP server meant the model could call **any** of its tools unprompted — `AgentRunner` went straight from "the response contains tool calls" to `MCPToolRegistry.executeTool()`. For a stdio server that can touch the filesystem or drive a browser, that's a real risk. Every MCP tool call now passes a permission gate first.

- **Three states, and `'ask'` is ALWAYS the default.** A tool with no explicitly stored setting prompts the user. This is the entire point of the feature — if you ever change the resolution chain, the thing to re-verify is that an *unconfigured* tool still ends at `'ask'`, never `'allow'`.
- **Where the default is enforced** (four independent layers, all failing safe):
  1. `MCPStore.normalizePermission()` returns `'allow'`/`'decline'` **only** for those two exact literal strings and `'ask'` for everything else — missing key, missing map, non-object map, `null`, `true`, `'ALLOW'`, a corrupted record. Every read goes through it.
  2. `MCPStore.getToolPermission()` returns `'ask'` for an unknown server id or empty tool name.
  3. `MCPToolRegistry.getToolPermission()` returns `'ask'` when the qualified name isn't in `toolIndex` at all (server disabled/removed/never listed).
  4. `chatView.js`'s `requestToolPermission()` falls back to prompting if the permission read throws, and `AgentRunner` treats a **throwing** `onPermissionRequest` callback as `'decline'`.
- **Storage shape**: `server.toolPermissions`, an object on each server record keyed by the tool's **own raw name** (`browser_navigate`), *not* the `server__tool` qualified name used for provider function-calling. `'ask'` is stored as **absence of the key** (`setToolPermission(..., 'ask')` deletes it), so "never configured" and "explicitly set back to Ask" are the same state and the map stays small. `save()`'s defaults include `toolPermissions: {}`, and `mcpView.js`'s `readFormValues()` spreads the full original record first, so the map survives a normal "Save Profile" edit (verified). Editing the raw `mcp_config.json` **does** drop permissions, since `parseJSONConfig` rebuilds server objects from scratch — that resets everything to `'ask'`, i.e. it fails in the safe direction.
- **The gate lives in `AgentRunner.run()`'s tool loop**, as `callbacks.onPermissionRequest(call) => Promise<'allow'|'decline'>`, awaited **before** `onToolExecuting` fires — deliberately, so the violet "tool is running" spinner box never appears while we're actually still waiting on the user. On `'decline'`, `MCPToolRegistry.executeTool()` is **not called at all**; instead the entry is traced as `{name, args, result: TOOL_DECLINED_NOTICE, declined: true}` and the same notice is pushed into `payload` as a `{role:'tool', ...}` message, so the model learns the call didn't happen and reacts in character instead of hanging or hallucinating a result. Following the file's existing convention, an **absent** callback defaults to `'allow'` (an optional callback must not change behavior for hypothetical non-UI callers) — but **both** `chatView.js` call sites always supply it; leaving either unwired silently restores the old unprompted behavior.
- **Abort safety**: the tool loop re-checks `signal?.aborted` at the top of every call iteration and throws `AbortError`, so hitting stop while a prompt is open (or while an earlier call in the same round is running) doesn't run the remaining calls or fire a doomed extra provider request. The prompt itself also resolves as `'decline'` on `signal`'s abort event, and both generation paths call `removeToolPermissionPrompt()` in their `finally`.
- **Settings UI**: `MCPView.renderToolPermissions(hostEl, serverId)` is the single implementation, rendered in two places (same pattern as the master/immersive switches): the `#mcp` route's per-server "Tool Permissions" expander (primary location) and the chat right-drawer MCP tab's "Permissions" expander. Both load **lazily on first expand** — it needs a live `tools/list` round trip, so loading it for every card on render would fire one per server. It lists every currently-discovered tool plus any stored-but-no-longer-discoverable ones (so an override stays visible/removable when a server is offline), each with a `.perm-seg` 3-way segmented control (slate Ask / emerald Allow / rose Decline, styled in `css/components.css`), plus a one-click bulk **"Set semua: Ask / Allow / Decline"** row that writes every tool at once via `setAllToolPermissions()` and updates the on-screen controls in place rather than re-rendering (which would re-fire discovery). Expanding the panel on the `#mcp` page sets `gridColumn: '1 / -1'` on the card so the list gets the full row width.
- **Regression invariant still holds**: this whole mechanism only engages inside `AgentRunner.run()` once `toolCalls.length > 0`, which already implies tools were active. A chat with no enabled MCP servers never asks anything and is byte-for-byte unchanged.

## 🔒 XSS / sanitization approach

- `js/utils/sanitize.js` exports `escapeHtml`/`escapeAttr`; nearly every view escapes character/persona/message/proxy fields before interpolating into `innerHTML` template strings. This is the app's only XSS defense (no DOM-diffing framework, no CSP meta tag) — when adding new UI that renders character-card, persona, or chat-message fields, escape them the same way existing code does nearby.
- `Modal.open({ title, contentHTML })` does **not** escape `title` or `contentHTML` itself — every current call site pre-escapes any dynamic (character/persona-controlled) title with `escapeHtml()` before passing it in. If you add a new `Modal.open()` call with a dynamic title, escape it manually — the same way `chatView.js`/`charactersView.js`/`personasView.js`/`proxiesView.js` already do.

## ⚙️ Rules & Guidelines for Code Modders

1. **No Emojis**: Always use clean text labels or SVG icons in UI buttons, toasts, and headers.
2. **Flat themeable slate**: Maintain the flat slate look, but **never write a raw colour**. Every colour must come from a token in `css/variables.css` (`var(--bg-surface)`, `var(--text-main)`, `var(--border-light)`, …) — including inside JS template strings, which is where the old hardcoded hex lived. If a shade you need has no token, add one to *both* the light block and *both* dark blocks rather than inlining it, and re-check the result in light and dark.
3. **Dedicated Chat View**: Keep the chat view fullscreen with back-button navigation.
4. **Floating Input Box**: Keep the chat input box floating over the bottom area (`bottom: 24px`) with a full-height message stream behind it.
5. **Right Drawer Tabs**: Keep Sessions and Options separated into distinct tabs in the right drawer.
6. **Use the shared widgets**: a new boolean setting uses `toggleSwitchHTML`/`toggleRowHTML`, not a bare `<input type="checkbox">`; a new choice field uses `dropdownHTML` + `wireDropdown`, not a native `<select>`. Both are drop-in with the old read paths (`.checked` / `.value`).
7. **Escape before interpolating**: any new template string that embeds character/persona/message/import-derived data must go through `escapeHtml`/`escapeAttr` (see XSS section above) — this is the only sanitization layer in the app.
8. **Electron IPC surface stays minimal**: don't add new `ipcMain`/`contextBridge` handlers without a real need — the app's whole security model relies on `nodeIntegration: false` + a narrow, fully-typed `preload.js` (currently: window controls + the 3-method MCP stdio bridge). Never expose a generic/passthrough IPC channel.
